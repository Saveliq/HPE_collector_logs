# Экспорт аудита DELL в Excel

Запуск из корня репозитория: `python DELL/toExel/main.py`. Выберите папку с собранными
JSON или ZIP. Результат — `Аудит_результаты.xlsx` в выбранной папке.

Зависимости: Python 3 с Tkinter и `openpyxl` (`python -m pip install -r DELL/toExel/requirements.txt`).
Обрабатываются выгрузки коллектора `redfish_full.json`, в том числе во вложенных папках.

Парсер использует `/redfish/v1/Systems/System.Embedded.1`,
`/redfish/v1/Chassis/System.Embedded.1` и `/redfish/v1/Managers/iDRAC.Embedded.1`.
Поддерживаются контроллеры из `StorageControllers` и `Controllers`, диски SATA/SAS/NVMe,
БП и вентиляторы из старых `Power`/`Thermal` и новых `PowerSubsystem`/`ThermalSubsystem`.
P/N серверов берётся из `PartNumber`, Dell Service Tag — из `Oem.Dell.ServiceTag`
корневого ресурса Redfish (при отсутствии — из `System.SKU`).
На листе **Аудит** второй столбец — **Dell Service Tag**, заполненный только для серверов.
Отдельного столбца S/N на этом листе нет.
Серийный PPID диска не используется как P/N; при отсутствии P/N используется модель.
Сетевые карты учитываются по физическим адаптерам, включая FC HBA; порты не увеличивают количество карт.
Прошивки `Current` и `Installed` объединяются, `Previous` сохраняется с отдельным назначением.

Основной лист **Аудит** содержит инвентаризацию и отдельные колонки прошивки,
State, Health, HealthRollup и DIMMStatus. В строке сервера
в колонке «Версия прошивки» указаны BIOS и iDRAC через точку с запятой.
Также указаны политика питания SysProfile (при отсутствии — ProcPwrPerf),
**Redundancy Policy**, **Hot Spare**, **Primary PSU** и отдельное **Потребление, Вт**.
Настройки БП берутся из `Attributes` ресурса
`/redfish/v1/Managers/iDRAC.Embedded.1/Oem/Dell/DellAttributes/System.Embedded.1`:
`ServerPwr.1.PSRedPolicy`, `ServerPwr.1.PSRapidOn`, `ServerPwr.1.RapidOnPrimaryPSU`
соответственно. Отсутствующие значения остаются пустыми. Колонка
«Включение после потери питания» не выводится.
Потребление берётся из `PowerConsumedWatts` массива
`/redfish/v1/Chassis/System.Embedded.1/Power#/PowerControl`, а не из мощности блоков питания.
При наличии нескольких областей питания используется единственная запись
MemberId=0 или PhysicalContext=Chassis; пересекающиеся показания не суммируются.
Основной ответ `/Power` имеет приоритет над его повторными ответами по ссылкам с `#`.
Столбец Quantity удалён: строка инвентаризации уже соответствует одному компоненту.

Строки серверов выделены жирным шрифтом. Цветные темы таблиц, заливки заголовков
и чередование цветов строк не используются. Подробные показания температур
на основном листе не выводятся; датчик с проблемным Health попадёт в лист Health.

В итоговом файле пять листов. При открытии выбран **Сводка_серверов**.

1. **Аудит** — серверы и их компоненты.
2. **Группировка_PN** — количество компонентов по P/N для каждого сервера.
   Это фактическое количество, поэтому колонка количества здесь сохранена.
3. **Сводка_серверов** — показатели всего парка: число серверов, моделей,
   серверов с Health != OK, различных версий BIOS и iDRAC. Ниже таблица комбинаций
   «Модель сервера + BIOS + iDRAC»: количество, доля от всех серверов этой модели
   и список S/N. Например, 100 серверов одной модели дают строки 80 (80%) и 20 (20%).
   Далее расположены независимые сводки BIOS и iDRAC по моделям.
   Показатель Health считает уникальные серверы с проблемами самого сервера
   или любого компонента, включая HealthRollup. Неизвестные модели и версии
   не включаются в число различных моделей/версий, но серверы остаются в таблицах.
4. **Микрокоды** — группировка по типу компонента, модели/P/N устройства,
   Firmware и назначению прошивки по всему парку. Отдельные количества **Серверов**
   и **Компонентов**: три сервера с двумя одинаковыми SSD дают 3 и 6.
   Модели и S/N серверов на этом листе не выводятся. MAC-адреса в названиях
   сетевых карт не разделяют одинаковые модели на разные группы.
   CPU, RAID, FC HBA, диски, БП и прочие устройства
   учитываются по физическим экземплярам, а не по числу ответов Redfish.
   Без S/N устройства различаются по исходному пути. Модель и слот используются
   для сопоставления разных представлений одного контроллера, в том числе BOSS и PERC.
   Резервные версии и MicrocodePatches по CpuId отделены колонкой
   «Назначение прошивки». MicrocodePatches — доступные патчи, а не утверждение,
   что каждый из них сейчас активен. Для системных прошивок считается экземпляр
   соответствующего элемента прошивки на сервере. Один компонент может иметь
   несколько назначений прошивки; складывать такие строки как число устройств нельзя.
5. **Health** — только отклонения Health/HealthRollup от OK. Показаны S/N сервера,
   модель, компонент, P/N и S/N компонента, State, Health, Firmware, HealthRollup,
   имя/модель компонента, путь Redfish и исходный файл.
   Общий проблемный Health сервера выводится отдельной строкой «Сервер», даже
   если конкретный неисправный компонент определить не удалось. Пустые значения
   не считаются неисправностью; явный Unknown включается. История событий и
   отложенные настройки исключаются. Статусы лицензий (`LicenseService/Licenses`
   и Dell OEM licenses) исключаются из аппаратного Health и счётчика проблемных
   серверов: у лицензий отсутствуют аппаратные P/N и S/N, а их Health не является
   состоянием оборудования. Статусы лицензий сохраняются в исходной диагностике.

На новых листах есть фильтры и закреплённые заголовки. Количества и доли
рассчитаны по всей выгрузке, фильтрация не меняет их знаменатели.
Старые листы **Модели_и_прошивки** и **Health_не_OK** больше не создаются.
Структура и расчёты **Группировка_PN** сохранены.

Повторный JSON того же сервера пропускается на всех листах. Повторные полные
ответы по ссылкам с `#` не дублируют диагностические данные. Совпадающие статусы
одного устройства объединяются; различающиеся статусы сохраняются с исходными путями.

В отчёт попадают только сведения из выгрузки: отсутствующие версии, показания
и статусы оставляются пустыми. Ноль и False сохраняются.
В колонках состояний нормальные значения (OK, Enabled, GoodInUse, Up,
LinkUp, Operational) выделяются зелёным. **Warning выделяется жёлтым**,
Critical и остальные ошибки (Failed, Error, Degraded, MapOutError,
MapOutConfiguration, DegradedA3DC) — красным. Для Critical и Warning
добавлено условное форматирование.
Неизвестные состояния и отсутствие компонента остаются без подсветки.
Цвет применяется к ячейкам статуса, а не к совпадающим словам
в названиях компонентов или версиях прошивки.

## Проверка

Установите зависимости проекта и из его корня выполните:

```powershell
python -m unittest discover -s DELL/toExel/tests -v
```

Тесты используют десять эталонных файлов `DELL/toExel/examples/**/redfish_full.json`
и синтетический парк с группами 80/20. Проверяются потребление,
пустые данные и нули, комбинации и независимые сводки BIOS/iDRAC, проценты,
счётчики серверов/компонентов (3 сервера / 6 SSD), микрокоды CPU, резервные версии,
общий Health сервера, сведения о проблемных БП, дубли серверов и ссылок,
фильтры, пять итоговых листов, активный лист, сохранение XLSX,
цвета статусов, счётчики P/N и повторный запуск экспорта.
